## 1. Architecture Overview

Application Tracker is a full-stack web application built with Next.js and TypeScript.

The application uses a single repository and a modular monolith architecture. The frontend, server-side application logic, validation, authentication, and database access live in the same codebase while remaining separated by responsibility.

This approach keeps deployment and development simple while allowing the codebase to grow without placing unrelated logic inside route files or UI components.

## 4. Architectural Style

The application will use a modular monolith.

A modular monolith keeps the application inside one deployable codebase while organizing business logic into distinct feature modules.

Each feature should own its:

- Components
- Validation schemas
- Types
- Server-side operations
- Data-access logic
- Tests

Business logic should not be placed directly inside pages, route handlers, or React components when it can be moved into a feature module.

## 6. Folder Responsibilities

### `src/app`

Contains Next.js routes and route-level files.

Examples:

- Pages
- Layouts
- Loading states
- Error boundaries
- Route handlers
- Route-specific metadata

Route files should remain small. Business logic should be delegated to feature modules or shared server modules.

### `src/components/ui`

Contains reusable presentation components that are not tied to a specific business feature.

Examples:

- Button
- Input
- Select
- Modal
- Dialog
- Badge
- Table
- Card
- Pagination

These components must not access the database directly.

### `src/components/layout`

Contains reusable application layout components.

Examples:

- Header
- Sidebar
- Navigation
- Page container
- Mobile navigation

### `src/features`

Contains business-feature modules.

The first feature module is:

```text
src/features/applications
```

Application-specific logic should remain inside this module unless it is genuinely shared by other features.

### `src/features/applications/components`

Contains React components used specifically for job applications.

Examples:

- Application form
- Application card
- Application table
- Status badge
- Filter controls
- Kanban column

### `src/features/applications/schemas`

Contains Zod schemas used to validate application data.

Examples:

- Create-application schema
- Update-application schema
- Filter schema

Validation schemas should be reusable between forms and server-side operations.

### `src/features/applications/server`

Contains server-only application logic.

Examples:

- Creating an application
- Updating an application
- Deleting an application
- Fetching application records
- Verifying resource ownership
- Calculating dashboard statistics

Files in this directory must not be imported into client components.

### `src/features/applications/types`

Contains application-specific TypeScript types that are not generated by Prisma or inferred from Zod.

### `src/lib`

Contains shared utilities and third-party configuration.

Examples:

- Prisma client
- Date utilities
- Environment validation
- Logging helpers
- Formatting utilities
- Shared constants

### `src/server`

Contains server-only logic shared across multiple features.

Examples:

- Authentication helpers
- Authorization helpers
- Database utilities
- Shared server errors

### `src/hooks`

Contains reusable React hooks.

Hooks should only be created when React state or lifecycle behavior is genuinely reusable.

### `src/types`

Contains types shared across multiple features.

Feature-specific types should remain inside their feature directory.

### `tests`

Contains tests that do not belong directly beside a source file.

Examples:

- End-to-end tests
- Integration tests
- Shared test utilities
- Test fixtures

## 7. Data Flow

A typical application creation request should follow this path:

```text
User submits form
        |
        v
Client or Server Component
        |
        v
Zod validation
        |
        v
Server Action or Route Handler
        |
        v
Authentication check
        |
        v
Application service
        |
        v
Prisma
        |
        v
PostgreSQL
```

The server must validate all incoming data even when validation already occurs in the browser.

Client-side validation improves the user experience but does not replace server-side validation.

## 8. Server and Client Component Rules

React Server Components should be used by default.

Client Components should only be used when a component requires:

- Browser APIs
- Event handlers
- Local interactive state
- React hooks
- Drag-and-drop behavior
- Client-side form interactions

The `"use client"` directive should be placed as low in the component tree as practical.

Database access, secrets, authentication checks, and authorization logic must remain server-side.

## 9. Data Access Rules

Prisma will be the only layer that communicates directly with PostgreSQL.

Database queries should:

- Select only required fields
- Include ownership conditions
- Avoid exposing private user data
- Use transactions when multiple dependent writes must succeed together
- Handle expected database errors

UI components must not call Prisma directly.

Database operations should be called through server-side feature functions.

## 10. Authentication and Authorization

Authentication answers:

> Who is the current user?

Authorization answers:

> Is the current user allowed to perform this action?

Every protected database operation must verify that the requested record belongs to the authenticated user.

Authorization must occur on the server.

Hiding an edit or delete button in the interface is not sufficient protection.

Example ownership rule:

```text
application.userId must equal authenticatedUser.id
```

## 11. Validation

Zod schemas will validate:

- Form input
- Route parameters
- Query parameters
- Filter values
- Environment variables

Validation errors should be converted into understandable messages for the user.

The application should not trust:

- Browser-submitted values
- URL parameters
- Query strings
- Hidden form fields
- Client-side application state

## 12. Error Handling

Expected errors should be handled explicitly.

Examples:

- Invalid form input
- Unauthenticated request
- Unauthorized record access
- Record not found
- Duplicate data
- Database failure

The interface should provide:

- Clear validation errors
- Useful empty states
- Loading indicators
- Success feedback
- Error recovery options

Sensitive server details must not be exposed to the browser.

## 13. Security Principles

The application must:

- Keep secrets in environment variables
- Exclude `.env` files from Git
- Validate all user input
- Verify record ownership server-side
- Avoid exposing database models unnecessarily
- Avoid logging secrets or authentication tokens
- Use secure authentication sessions
- Keep server-only modules out of client bundles

An `.env.example` file may document required environment variables without containing real secrets.

## 14. Testing Strategy

### Unit Tests

Unit tests should cover isolated logic such as:

- Validation schemas
- Date calculations
- Status transitions
- Dashboard calculations
- Formatting utilities

### Component Tests

Component tests should cover important interface behavior such as:

- Form validation messages
- Status changes
- Filter controls
- Confirmation dialogs

### Integration Tests

Integration tests should cover interactions between:

- Server Actions
- Authorization rules
- Application services
- Database operations

### End-to-End Tests

End-to-end tests should cover critical user workflows:

1. Create an account.
2. Sign in.
3. Create an application.
4. Edit the application.
5. Change its status.
6. Set a follow-up date.
7. Delete or archive the application.

Changes should be merged through pull requests.

Each pull request should include:

- Related issue
- Changes made
- Testing performed
- Screenshots for interface changes

## 17. Architecture Decisions

### ADR-001: Single Repository

**Decision:** Use one repository for the frontend and backend.

**Reason:** Next.js supports both interface and server-side functionality, allowing faster development and simpler deployment.

### ADR-002: Modular Monolith

**Decision:** Organize the application by feature within a single deployable application.

**Reason:** This provides clear boundaries without introducing unnecessary microservice complexity.

### ADR-003: PostgreSQL

**Decision:** Use PostgreSQL as the primary database.

**Reason:** The product contains relational data, ownership relationships, filtering, and analytics that fit a relational database.

### ADR-004: Prisma

**Decision:** Use Prisma for schema management, migrations, and database access.

**Reason:** Prisma provides TypeScript integration, migration tooling, and readable database queries.

### ADR-005: Server-First Rendering

**Decision:** Use React Server Components by default.

**Reason:** Most dashboard data can be loaded securely on the server while reducing unnecessary client-side JavaScript.

## 18. Open Architecture Decisions

The following choices remain unresolved:

- Authentication provider
- PostgreSQL hosting provider
- Whether application records will support permanent deletion, archiving, or both
- Whether the first dashboard will use a table, Kanban board, or both
- Whether server mutations will primarily use Server Actions or Route Handlers
- Whether tests will use a local test database or isolated test containers
